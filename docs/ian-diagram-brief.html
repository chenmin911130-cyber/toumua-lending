1. What the system is

Toumu’a Lending is a school-built loan workspace for a small Auckland lending office. Staff and customers use a web app. Office staff can also open the same staff screens in a desktop window (Electron). One API and one PostgreSQL database sit behind both clients.

The supported business is:

  1. A loan officer and borrower complete an application and record collateral.
  2. A valuation officer records a valuation.
  3. A manager approves or declines.
  4. Collateral is received, inspected, and stored.
  5. A cashier disburses the loan, then records repayments and issues receipts.
  6. On settlement the collateral is returned. On default it may be sold and the proceeds recorded.

Interest currently uses a labelled demo policy (21% p.a. simple interest) so the demo can approve loans. This is not Alice’s official office formula. Do not draw it as a confirmed business rule. Write “demo placeholder pending client confirmation” on any figure that mentions rates.

6. Figure-by-figure instructions

Figure 1 — System context

One box in the centre: Toumu’a Lending Workspace.

  • Left/top people: Customer, Loan officer, Valuation officer, Cashier, Manager, Owner/admin.
  • Right systems: PostgreSQL, Email adapter, Railway host (optional, or fold into the centre box).
  • Office / Alice as an external information source (official rates), not a daily login.

Arrows are information, not every API call. Example labels: “application and payments”, “receipts and balances”, “invite / verify email”, “persist loans”.

Figure 2 — Use case diagram

Group use cases. Stick-figure actors outside the system boundary.

  • Identity: Register, verify email, sign in, reset password, accept staff invitation.
  • Origination: Maintain borrower, create application, add collateral, record valuation, submit, approve/decline.
  • Servicing: Intake collateral, disburse, record repayment, issue receipt, correct a transaction.
  • Close: Return collateral; declare default; record sale; record sale proceeds.
  • Customer portal: View my loans, schedule, security photos, notifications.

Include relationships only where they are real: «include» submit → completeness checks; approve «extend» decline as two outcomes of “Decide application”.

Figure 3 — Activity diagram, happy path

Swimlanes: Loan officer | Valuation officer | Manager | Cashier | Customer (optional, for viewing).

Happy path only:

Create borrower → draft application (five steps) → valuation completed → submit → manager approves → collateral RECEIVED / INSPECTED / STORED → cashier disburses (loan becomes ACTIVE) → repayments until balance is 0.00 (SETTLED) → valuation officer returns collateral (RETURNED).

Show a decision after review: Approve / Decline. Decline is a stop, not the default path.

Figure 4 — Activity diagram, default path

Starts from an ACTIVE loan. Manager declares DEFAULTED (reason required). Valuation officer records a sale. Cashier records sale proceeds. Surplus or shortfall is reported. If the debt is fully recovered the loan becomes SETTLED; collateral is SOLD, not returned.

Do not invent an automatic “overdue = default” transition.

Figure 5 — Application and loan states

Two regions on one page is fine.

  • Application: DRAFT → SUBMITTED → APPROVED | DECLINED. No arrow back from SUBMITTED except through a new application (do not draw “unsubmit”).
  • Loan is created only on APPROVED: APPROVED_UNFUNDED → ACTIVE → SETTLED. From ACTIVE a manager may move to DEFAULTED. From DEFAULTED, full recovery may move to SETTLED.

Figure 6 — Collateral states

PROPOSED → VALUED → STORED → RETURNED (settled loan) or SOLD (after default). Custody events sit on the arrows (RECEIVED, INSPECTED, STORED, RETURNED, SOLD).

Figures 7–10 — Week 3 only (preview so you can plan)

ERD (logical). Main entities and the relationships. You do not need every column.

  • User 1—* Session, Invitation, Notification, AuditEvent
  • User *—* Borrower through BorrowerAccountLink
  • Borrower 1—* Application, Loan
  • Application 1—1 ApplicationTerms, 1—* ApplicationAsset, 0—1 Loan, 0—1 ApplicationDecision

Architecture. Customer browser and staff browser (and Electron) → Web (Railway) → API (Railway) → PostgreSQL. Secrets stay on the API. Desktop does not talk to the database.

Sequence — sign in. Browser → POST /auth/login → API checks password → session cookie (HttpOnly) → GET /auth/me.

Sequence — repayment. Cashier → idempotent POST repayment → API quotes allocation → writes ledger + updates schedule → receipt. Replay of the same key returns the original result.
